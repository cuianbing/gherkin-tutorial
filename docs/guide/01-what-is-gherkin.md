# 第 1 篇 · 认识 Gherkin：背景、是什么、能干什么

> 本篇零代码。读完你将明白：Gherkin 为什么会出现（BDD 运动的产物），它到底是一门什么"语言"，能为团队解决什么问题，以及它不适合做什么。

---

## 一、背景：从一个古老的痛点说起

### 1.1 需求方和实现方，永远在"翻译"

软件开发里有一条恒久的裂缝：**懂业务的人不写代码，写代码的人不懂业务**。传统分工下，需求的传递链条是：

```text
产品经理(写 PRD) → 开发(读 PRD 写代码) → 测试(按 PRD 写测试用例)
```

每一环都是一次"人工翻译"，翻译就会失真。典型事故现场：

- PRD 写"密码错误 5 次锁定账户"——第 6 次输入正确密码，能解锁吗？锁定多久？没说清楚，开发按自己的理解做；
- 测试用例写在 Excel 里，需求改版后用例就过时了，和系统行为越来越对不上；
- 上线后发现的行为和产品脑中的行为不一致，三方各执一词，回头翻文档——文档还是三个月前的。

**根因：需求文档、测试用例、自动化代码是三套割裂的东西，描述的是同一个系统，却没有一个"共同语言"。**

### 1.2 BDD 的诞生：让"行为的描述"本身可以被执行

软件行业为此演进了一条路：

| 时间 | 事件 | 贡献 |
| --- | --- | --- |
| 2003 | Kent Beck 的 TDD 已流行多年，但 Dan North 等人发现：开发者常把 "test"（测试）误解为"验证代码写对了"，忽视"描述系统应该有什么行为" | BDD 思想萌芽 |
| 2003 | Eric Evans 出版《领域驱动设计》，提出 **Ubiquitous Language（统一语言）**——团队所有人用同一套业务词汇交流 | 提供理论根基 |
| 2006 | Dan North 发表《Introducing BDD》正式提出 **BDD（Behavior-Driven Development，行为驱动开发）**；同期的 Chris Matts 面向业务分析者提出 **Given-When-Then** 描述模板 | 方法论成型 |
| 2008 | Aslak Hellesøy 发布 **Cucumber**（Ruby），把 Given-When-Then 文本**变成可执行测试** | 工具落地 |
| 2009 之后 | 描述行为的文本被抽离成一门独立的格式语言——**Gherkin**，Cucumber、behave、Behat 等各语言工具共用同一语法 | 语言标准化 |

BDD 的核心主张一句话：**先由业务方、开发、测试三方（"三 amigos"）用具体例子讨论清楚"系统该有什么行为"，再把这个行为描述写成"既是需求文档、又是测试用例、又能自动执行"的单一文件。** 这个文件的语言就是 Gherkin。

> **Gherkin 这个名字**：Cucumber（黄瓜）工具的配套语言，Gherkin 即"腌黄瓜"——一脉相承的命名玩笑。它是开源规范（MIT 协议），任何工具都可以实现它的解析器。

## 二、Gherkin 是什么

**Gherkin 是一门用近乎自然语言写的、有严格结构的"行为描述语言"**。三个关键词展开：

### 2.1 它长得像自然语言（业务人员读得懂）

```gherkin
功能: 账户登录
  作为一名注册用户
  我希望用账号密码登录
  以便访问我的个人信息

  场景: 密码正确时登录成功
    假如 用户已在登录页
    当 用户输入正确的账号和密码并提交
    那么 应跳转到个人首页
```

这就是一个合法的 Gherkin 文件——没有括号、没有分号，产品经理 30 秒能读懂。**它默认甚至支持全中文关键词**（`功能`、`场景`、`假如`、`当`、`那么`……见第 2 篇）。

### 2.2 它有严格结构（机器解析得了）

看似随意，实际每一行都有语法角色：`功能:` 定义一个特性，`场景:` 定义一个用例，`假如/当/那么` 三段式描述行为。结构化带来两个能力：

- **可以被解析和校验**（写错关键词会报错）；
- **可以被绑定执行**——`假如 用户已在登录页` 这一行，可以映射到一段自动化代码；所有场景合并起来就是一套可重复运行的回归测试。

### 2.3 它是纯文本（放进代码仓库里管理）

Gherkin 文件（`.feature`）与代码同仓库、同评审、同版本。需求变更 = 修改 feature 文件 → 评审可见 → 测试同步更新，不再有"文档三个月没更新"的问题。

**一句话定义：Gherkin 是 BDD 实践中使用的、面向业务可读的、结构化的行为描述语言；Cucumber 等工具把它变成可执行的验收测试。**

注意区分两个名字（新手最容易混）：**Gherkin 是语言/格式，Cucumber 是解析并执行它的工具**（就像 SQL 是语言、MySQL 是引擎）。

## 三、能干什么：四大价值

| 价值 | 说明 |
| --- | --- |
| **① 需求实例化，消灭歧义** | 写 Gherkin 必须用具体例子（"余额 100 元时取 150 元 → 应失败"），抽象 PRD 里藏着的边界问题会在讨论时暴露。三方一起写场景的过程，本身就是最好的需求评审 |
| **② 一份文档三重身份** | 同一个 `.feature` 文件 = 需求文档（产品确认）+ 测试用例（测试设计）+ 自动化脚本骨架（开发绑定），彻底告别三套文档互相矛盾 |
| **③ 活文档（Living Documentation）** | 场景跑不过 = 文档与行为不符 = 要么代码错了要么文档旧了。文档被迫与系统行为保持同步，这是传统 Excel 用例永远做不到的 |
| **④ 回归测试资产** | 每个场景自动执行、输出报告（谁过了谁挂了、挂在哪一步），CI 里每天全量回归，防止"改了 A 坏了 B" |

## 四、生态全景：谁在读 Gherkin

Gherkin 是语言，"执行器"由各语言生态提供（写作时点）：

| 工具 | 语言 | 说明 |
| --- | --- | --- |
| **Cucumber-JVM** | Java/Kotlin | 7.34.x，企业使用最广，第 4 篇主角 |
| **Cucumber-JS** | JavaScript/TypeScript | 13.x，前端/Node 团队，第 5 篇 |
| **behave** | Python | 1.3.x，Python 侧主流选择 |
| **Reqnroll** | C#/.NET | 开源；**SpecFlow 已于 2024 年底 EOL**，这是官方指定继任者 |
| **Behat** | PHP | 老牌 PHP 生态 BDD 工具 |
| **Cucumber Studio** | （SaaS） | 商业平台，无需绑定代码也能管理场景 |

此外还有 pytest-bdd（Python）、cucumber-rs（Rust）等。**语法是同一套，学会 Gherkin 一处投入、处处可用。**

## 五、适用边界：它不适合做什么

诚实地说清边界，才能用好它：

| 适合 | 不适合 |
| --- | --- |
| 业务验收标准（登录、下单、退款规则） | 单元测试（验证函数内部逻辑——用 JUnit/Jest 直接写更快） |
| 业务规则的正例/反例枚举 | 性能/压力测试（用 JMeter/k6） |
| 跨系统端到端业务流回归 | 探索性测试（人的创造性活动，无法脚本化） |
| 团队需求沟通的"共同文档" | 纯技术性的底层行为（如"缓存过期策略"——业务方读不懂的场景不要硬凑 Gherkin） |

经验法则：**每个 feature 文件都应该值得给产品经理看**。如果一个场景业务方看不懂或不想看，它大概率不该用 Gherkin 写。

## 六、小结

- Gherkin 起源于 BDD 运动：把"需求—测试—代码"三套割裂的东西，统一成一份**业务可读、可执行、可版本化**的行为描述；
- 它长得像自然语言、结构严格、纯文本管理；**Gherkin 是语言，Cucumber 是执行工具**；
- 四大价值：实例化需求、一份文档三重身份、活文档、回归资产；
- 生态覆盖 Java/JS/Python/.NET/PHP，语法通用；
- 边界：管"业务行为"，不管单元细节、性能与探索性测试。
