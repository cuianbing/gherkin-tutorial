# 第 6 篇 · 场景案例合集：5 个真实业务形态

> 5 个案例覆盖 5 种典型形态：**纯业务规则**（ATM）、**结构化数据**（购物车）、**标签组织**（登录回归）、**API 测试**（下单接口）、**全中文工程**（中文 feature + 中文绑定）。每个案例给出 feature 全文与要点讲解，绑定代码演示关键片段（工程骨架见第 4 篇，不重复）。

---

## 案例一：ATM 取款（纯业务规则，三层拆解的教科书）

**背景**：ATM 是 BDD 教学的经典案例——规则清晰、边界丰富。业务规则：单次取款上限 2000 元；余额不足不能取；密码错误 3 次吞卡。

```gherkin
功能: ATM 取款

  规则: 单次取款上限 2000 元

    场景: 取款 2000 元（恰好上限）成功
      假如 用户余额 3000 元 且银行卡有效
      当 用户申请取款 2000 元
      那么 应吐出 2000 元现金
      而且 余额应变为 1000 元

    场景: 取款 2001 元被拒绝
      假如 用户余额 3000 元 且银行卡有效
      当 用户申请取款 2001 元
      那么 应提示 "单次取款不能超过 2000 元"
      而且 不应吐钞
      而且 余额应保持 3000 元

  规则: 余额不足不能取款

    场景: 余额 100 元时取款 150 元失败
      假如 用户余额 100 元 且银行卡有效
      当 用户申请取款 150 元
      那么 应提示 "余额不足"
      而且 不应吐钞

  规则: 密码连续错误 3 次吞卡

    场景: 第 3 次密码错误后吞卡
      假如 用户已连续输错密码 2 次
      当 用户再次输入错误密码
      那么 应吞回银行卡
      而且 应提示 "请联系客服"
```

**要点讲解**：

1. **每条规则一个 Rule 分组**，组内场景全部围绕该规则（正例 + 边界反例）；
2. 边界值放在场景里显式可见（2000 恰好成功 / 2001 失败）——抽象 PRD 从不写这些，例子里全暴露；
3. 失败场景的 Then 用 `不应吐钞` + `余额应保持` **双向断言**（拒绝了动作，且没产生副作用）；
4. 绑定层提示：`当 用户申请取款 {int} 元` 一个 {int} 模式覆盖所有取款场景。

## 案例二：电商购物车（数据表 + 场景大纲）

**背景**：批量加购与金额计算，数据形态复杂——正好演示 Data Table 与 Examples 的分工。

```gherkin
功能: 购物车金额计算

  规则: 多件商品金额按单价×数量累加

    场景: 批量加购多件商品
      假如 购物车为空
      当 用户将以下商品加入购物车:
        | 商品名称 | 数量 | 单价  |
        | 苹果     | 2    | 5.00  |
        | 牛奶     | 1    | 12.50 |
      那么 购物车应显示总金额 22.50 元
      而且 商品种类数应为 2

    场景: 加购后删除全部商品
      假如 购物车中已有 22.50 元的商品
      当 用户清空购物车
      那么 购物车应显示总金额 0.00 元
      而且 应提示 "购物车是空的"

  规则: 会员享受 95 折（向下取整到分）

    场景大纲: 会员折扣计算
      假如 用户是 <会员等级>
      而且 购物车中有金额 <原价> 元的商品
      当 用户提交结算
      那么 应显示折后金额 <折后价> 元

      例子:
        | 会员等级 | 原价    | 折后价  |
        | 非会员   | 100.00  | 100.00  |
        | 会员     | 100.00  | 95.00   |
        | 会员     | 99.99   | 94.99   |
```

**要点讲解**：

1. **Data Table（步骤载荷）** vs **Examples（场景参数化）** 在同一文件各司其职：批量商品清单用前者，同一逻辑多组输入用后者；
2. 折扣规则特意放了 `99.99 → 94.99` 这种**取整边界**例子——业务确认这类例子时经常发现规则定义漏洞（是四舍五入还是截断？）；
3. 绑定层提示：Data Table 用 `table.asMaps()` 逐行读取（第 4 篇第八节）。

## 案例三：登录回归集（Tags 组织 + 全流程规则）

**背景**：一个成熟的登录模块，场景数量增长后用标签分层执行——冒烟快跑、回归全跑、进行中的场景隔离。

```gherkin
@登录
功能: 账户登录

  规则: 密码正确时登录成功

    @冒烟测试
    场景: 正确密码登录
      假如 已注册用户 "tom" 的密码为 "t1234567"
      当 用户使用账号 "tom" 密码 "t1234567" 登录
      那么 登录应成功

    @回归
    场景: 记住我 7 天内免登录
      假如 用户上次登录时勾选了"记住我"
      而且 距上次登录已过 3 天
      当 用户再次访问首页
      那么 应保持已登录状态

  规则: 密码错误时登录失败

    @冒烟测试 @回归
    场景: 错误密码提示
      假如 已注册用户 "tom" 的密码为 "t1234567"
      当 用户使用账号 "tom" 密码 "wrong" 登录
      那么 应提示 "用户名或密码错误"

    @回归 @慢
    场景: 连续错误 5 次后锁定 30 分钟
      假如 用户已连续输错密码 4 次
      当 用户再次输入错误密码
      那么 账户应被锁定
      而且 应提示 "账户已锁定,请 30 分钟后再试"

  规则: 第三方扫码登录

    @wip
    场景: 微信扫码登录成功
      假如 用户已安装微信并登录
      当 用户使用微信扫码
      那么 应使用微信账号自动注册并登录
```

**要点讲解**：

1. 标签分层：`--tags "@冒烟测试"` 2 分钟出结果（CI 每次提交跑），`--tags "@回归"` 全量（夜间跑），`not @wip` 隔离未完成场景；
2. 标签可叠加且可同时打在 Feature 与 Scenario（Feature 级标签对其下所有场景生效）；
3. `@慢` 标签让团队对"哪些场景耗时"有共识，优化有方向；
4. 一个文件多规则展示真实模块的形状：登录方式会越来越多（扫码/短信），按 Rule 继续加组即可。

## 案例四：下单 API 测试（DocString + 接口断言）

**背景**：对订单服务的 REST 接口做验收测试。**API 是 Gherkin 非常合适的战场**——断言的业务语义（订单状态、金额）比 UI 更直接。

```gherkin
功能: 创建订单接口

  背景:
    假如 系统中存在用户 "1001" 且其账户余额 100 元
    而且 系统中存在商品 "A001" 单价 10 元 库存 5 件

  规则: 正常下单

    场景: 用合法报文创建订单成功
      当 系统收到以下创建订单请求:
        """
        {
          "userId": "1001",
          "items": [{"sku": "A001", "qty": 2}]
        }
        """
      那么 应返回 HTTP 状态码 201
      而且 应返回订单号
      而且 订单状态应为 "待支付"

  规则: 库存校验

    场景: 购买数量超过库存
      当 系统收到以下创建订单请求:
        """
        {"userId":"1001","items":[{"sku":"A001","qty":99}]}
        """
      那么 应返回 HTTP 状态码 400
      而且 应返回错误码 "INSUFFICIENT_STOCK"
      而且 商品 "A001" 的库存应仍为 5 件

  规则: 幂等性

    场景: 相同请求重复提交只生成一个订单
      当 系统收到以下创建订单请求:
        """
        {"userId":"1001","items":[{"sku":"A001","qty":1}],"requestId":"req-888"}
        """
      而且 系统再次收到完全相同的请求
      那么 应只存在 1 个对应订单
```

**要点讲解**：

1. **Background 优雅承担"数据准备"**：两个 Given 为全部场景造好前置数据（绑定层里调用造数 API 或写库）；
2. Then 断言三层：HTTP 状态码 → 业务返回（订单号/错误码）→ **副作用校验**（库存没被扣、订单只有一条）——API 测试最容易漏的就是副作用；
3. 幂等规则用"重复请求"场景表达，`requestId` 之类的幂等键显式写在报文里，业务一眼看懂被测什么；
4. 报文细节（字段名、JSON 结构）出现在 Gherkin 里是**合理的**——对 API 测试来说，接口契约本身就是被测对象；这与第 3 篇"技术语言混入场景"并不矛盾（那个反模式指的是与业务无关的 UI 选择器之流）。

## 案例五：全中文工程（中文 feature + 中文绑定）

**背景**：团队决定 feature 与绑定层全中文，向业务方彻底透明。feature 部分与第 2 篇第十一节相同（`# language: zh-CN`），绑定层用中文注解包：

`LoginStepsZh.java`：

```java
import io.cucumber.java.zh_cn.假如;
import io.cucumber.java.zh_cn.当;
import io.cucumber.java.zh_cn.那么;
import org.junit.jupiter.api.Assertions;

public class LoginStepsZh {

    private final Map<String, String> users = new HashMap<>();
    private boolean loginOk;

    @假如("已注册用户 {string} 的密码为 {string}")
    public void 注册用户(String username, String password) {
        users.put(username, password);
    }

    @当("用户使用账号 {string} 密码 {string} 登录")
    public void 登录(String username, String password) {
        loginOk = password.equals(users.get(username));
    }

    @那么("登录应成功")
    public void 登录应成功() {
        Assertions.assertTrue(loginOk, "期望登录成功");
    }
}
```

**要点讲解**：

1. `io.cucumber.java.zh_cn` 包内置中文注解（`@假如/@假设/@假定`、`@当`、`@那么`、`@而且/@并且/@同时`、`@但是`），与英文注解完全等价，可混用但建议统一；
2. 方法名直接用中文（Java 合法），IDE 导航与报告显示全中文；
3. 注意 **Windows 终端编码**：feature/代码 UTF-8 保存，Maven 加 `-Dfile.encoding=UTF-8`，避免乱码误判；
4. 折中方案也常见：feature 中文、绑定层英文注解（第 4 篇主线写法）——按团队英文水平定，**一致性比风格本身重要**。

## 七、团队落地清单（全系列收官）

把前六篇收敛成一张可直接执行的落地清单：

| 阶段 | 动作 |
| --- | --- |
| **启动** | 选 1 个业务模块试点；三方跑一次 Example Mapping（第 3 篇）；确定标签字典（@冒烟/@回归/@wip/@慢） |
| **搭建** | 按第 4/5 篇搭好绑定工程；feature 进代码仓库走评审；CI 里接命令：提交跑 `@冒烟测试`，夜间跑 `@回归` |
| **日常** | 新需求先 Example Mapping 再写代码；DoD 增加"场景自动化通过"；失败先分"代码错/场景过期" |
| **迭代** | 绑定层抽公共步骤库（登录态、造数）；场景按 Rule 持续重组；季度清理过期场景与标签 |
| **红线** | 敏感数据不进 feature（用占位符+环境配置）；UI 细节不进场景（声明式红线）；每个场景可独立执行 |

**Gherkin 的本质**：它不只是一门写测试的语法，而是把"**需求讨论**"这件事本身工程化——例子写清楚的那一刻，文档、用例、自动化三者已经同步诞生。祝你的团队早日用上这件武器。
