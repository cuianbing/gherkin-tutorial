# 第 3 篇 · 写出好场景：方法与反模式（重点篇）

> 语法人人能学会，但"场景写得好不好"决定 Gherkin 是团队的沟通利器还是又一种垃圾文档。本篇不讲语法，专讲**怎么把业务规则变成好场景**，以及小白最容易踩的八类反模式。

---

## 一、核心原则：实例化需求（用具体例子说话）

抽象描述永远藏不住歧义，具体例子一写，漏洞自动暴露：

```text
抽象（PRD 常见写法）:
  "用户密码输错多次后应锁定账户"

实例化（Gherkin 要求的写法）:
  "用户连续输错密码第 5 次时，账户锁定 30 分钟"
  "锁定期间输入正确密码，提示锁定"
  "锁定 30 分钟后输入正确密码，登录成功"
```

把抽象句变成三个具体句子的过程中，你被迫回答："第 5 次"还是"第 6 次"？锁 30 分钟还是 1 小时？锁定期间正确密码算不算解锁？——**这些正是开发与测试上线后扯皮的问题。实例化需求的价值在写的过程中就兑现了，根本不用等执行。**

## 二、三层拆解：能力 → 规则 → 场景

拿到一个需求，按三层往下拆：

```text
能力（Feature）      ← 用户能做成什么事："会员订单优惠计算"
  └─ 规则（Rule）    ← 这条能力的每条业务规则："满100减20" "优惠不叠加" "优惠有上限"
       └─ 场景       ← 每条规则的具体例子：正常例子 + 边界例子 + 反例
```

**找规则的实用问句**（对每个 Feature 逐条过）：

1. 什么条件下这条能力**成立**？（正例）
2. 什么条件下它**不成立/被拒绝**？（反例）
3. **边界**在哪里？（刚好等于、差一点、极限值）
4. 有没有**叠加/互斥/上限**等组合规则？

以"满 100 减 20"为例，三层拆完的产出：

```gherkin
规则: 满 100 元减 20 元

  场景: 订单 100 元时减 20 元           # 边界:恰好等于
  场景: 订单 99.99 元时不减             # 边界:差一点
  场景: 订单 300 元时也只减 20 元       # 边界:单次上限(上不封顶?按业务定)

规则: 满减不与优惠券叠加
  场景: 已用优惠券的订单不再满减        # 互斥规则
```

**每条规则至少一个正例 + 一个关键反例**，这就是场景的"覆盖率公式"——比"测试用例覆盖率百分比"朴素但有效得多。

## 三、GWT 语义纪律：六条细则

| # | 细则 | 反例 → 正例 |
| --- | --- | --- |
| 1 | **Given 是"已成立的状态"**，用完成时/状态描述，不写动作 | ❌假如用户点击登录按钮 → ✅假如用户已在登录页且账号已填好 |
| 2 | **When 只有一个核心动作**，需要多个动作说明场景切错了 | ❌当用户登录且下订单且支付 → 拆成登录/下单/支付三个场景 |
| 3 | **Then 写"可观察的结果"**，不写实现细节 | ❌那么调用了 refund 接口 → ✅那么账户余额应增加 50 元 |
| 4 | **Then 断言完整闭环**：结果 + 对账（状态变化） | ✅那么应吐钞 80 元 **而且** 余额应变为 20 元 |
| 5 | **场景之间互不依赖**，每个场景能单独跑（不依赖前一个场景留下的数据） | ❌场景2 接着场景1 的购物车继续 → 每个场景自带 Given |
| 6 | **数据具体**，用真实感的值，别写"某用户""测试数据" | ❌假如用户余额为 X → ✅假如用户余额为 100 元 |

细则 5 最好联动自动化实现：每个场景执行前自动重置环境（第 4 篇的 Hook 里做），从机制上保证独立性。

## 四、声明式 vs 命令式：最重要的分水岭

**命令式（ Imperative）**——把操作步骤流水账写出来（UI 录制的味道）：

```gherkin
# ❌ 命令式:一步一步教机器怎么做,业务读不出任何意图
场景: 登录
  假如 用户打开浏览器
  当 用户访问 /login 页面
  并且 用户在 #username 输入 "tom"
  并且 用户在 #password 输入 "123456"
  并且 用户点击 #btn-submit
  然后 页面 url 变为 /home
```

问题：5 步操作没有体现任何业务规则；换一种登录方式（扫码）整个场景重写；页面元素变了（`#username`）所有场景跟着改。

**声明式（Declarative）**——只描述业务意图与结果，"怎么做"交给自动化层：

```gherkin
# ✅ 声明式:业务读者能看懂、能评审;实现细节下沉到步骤代码
场景: 密码正确时登录成功
  假如 注册用户 "tom" 的密码是 "123456"
  当 用户使用账号密码登录
  那么 用户应已登录并看到欢迎语 "欢迎回来, tom"
```

**判断标准一句话：把这个场景念给产品经理听，他能逐句点头且不关心你怎么实现，就是声明式。** UI 操作细节、API 调用、SQL 检查全部属于步骤绑定代码的世界。

## 五、反模式清单（八大坑）

| # | 反模式 | 症状 | 药方 |
| --- | --- | --- | --- |
| 1 | **UI 流水账** | 步骤全是点击/输入/跳转 | 见上节，下沉到绑定层 |
| 2 | **一个场景多个 When** | `当...并且当...并且当...` | 拆场景；或把前序动作降级为 Given（"已下单"） |
| 3 | **超长 And 链** | 一个 Then 里 And 了 5 个断言 | 拆成多个场景或提炼业务概念（"订单应为已取消状态"） |
| 4 | **场景标题没信息量** | "测试1""正常场景" | 标题=条件+结果的摘要 |
| 5 | **隐藏依赖链** | 场景 B 必须在场景 A 后跑 | 每场景独立 Given + 自动化重置环境 |
| 6 | **复制粘贴改数字** | 10 个几乎一样的场景 | 改用场景大纲 + 例子表 |
| 7 | **Background 塞满步骤** | 背景 8 行，场景 2 行 | 重新分组（Rule），背景只留公共大前提 |
| 8 | **技术语言混入场景** | "调用 POST /api/v1/xxx"（业务无关时） | 接口细节放绑定代码；除非"接口契约"本身是被测业务 |

## 六、Example Mapping：三方共写场景的轻量工作坊

Gherkin 场景不该由一个人闷头写——**Example Mapping**（实例映射）是 30 分钟的三方协作流程（产品+开发+测试围一桌）：

1. 拿一张**黄色卡片**写上本次要做的 User Story（能力）；
2. 每发现一条**业务规则**，记一张**蓝色卡片**贴在下面；
3. 每条规则下，用**绿色卡片**写一个支持它的具体例子；
4. 讨论中出现"还没想清楚"的问题，记**红色卡片**——这就是要拿回去澄清的需求问题。

产出直接翻译成 Gherkin：黄卡片=Feature，蓝=Rule，绿=Scenario，红=阻塞项。**Example Mapping 结束的那一刻，feature 文件其实已经写完了。**

没有线下条件时，用在线白板/表格同样可以跑。

## 七、团队协作流程建议

| 问题 | 建议 |
| --- | --- |
| **谁写场景？** | 产品/测试起草业务语言，开发补充边界与技术视角；**三方评审**是 BDD 的精髓，谁"拥有"文件反而是次要问题 |
| **什么时候写？** | 开发前（Example Mapping）定初稿；开发中补边界例；上线前冻结为回归资产 |
| **放哪里？** | 与代码同仓库 `src/test/resources/features/`（或独立 `features/` 目录），走代码评审 |
| **怎么算完成？** | Definition of Done 加一条："所有场景自动化执行并通过"——场景没跑通，需求不算交付 |
| **失败了算谁的？** | 先分清"代码错了"还是"场景过期了"：任一种都是正常修复对象，这正是活文档的自愈机制 |

## 八、小结

- 写场景的过程 = 需求评审的过程：**实例化需求**逼出所有歧义；
- 三层拆解公式：**能力 → 规则（问四类问题）→ 场景（每规则 ≥1 正例 + 关键反例）**；
- GWT 六条纪律；**声明式**是黄金标准（产品能听懂 = 合格）；
- 八大反模式对号入座；Example Mapping 是三方共写的标准流程。
