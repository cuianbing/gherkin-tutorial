# 第 2 篇 · Gherkin 语法详解（重点篇）

> 本篇不需要写代码，只需要一个文本编辑器。Gherkin 语法元素一共就 10 来个，一次讲全：从文件结构到关键词、场景大纲、数据表、DocString、Tags，最后是完整的中文写法与常见错误表。

---

## 一、文件与总体结构

- 特性文件以 **`.feature`** 结尾，**UTF-8 编码**（支持中文的前提）；
- 缩进约定为**两个空格表示层级**（与 Python 类似，缩进只是视觉约定，解析器主要认关键词）；
- 建议命名：`登录.feature` 或 `login.feature`，一个文件对应一个业务能力。

总体层级（从外到内）：

```text
Feature(特性)              ← 文件只有一个,最大业务能力
├── Rule(规则)             ← 0..n 条业务规则,组织场景
│   ├── Background(背景)   ← 可选,本规则下所有场景的前置
│   └── Scenario(场景)     ← 1..n 个具体例子
└── (Feature 级也可直接放 Scenario 与 Background)
```

一个完整骨架（先混眼熟，逐节拆解在后）：

```gherkin
@线上验收
功能: 会员订单优惠计算

  背景:
    假如 会员"小明"已登录

  规则: 满 100 元减 20
    场景: 订单金额恰好 100 元
      假如 购物车中有价值 100 元的商品
      当 提交订单
      那么 应优惠 20 元
      而且 应支付 80 元

  规则: 优惠不叠加
    场景: 已使用优惠券时不再享满减
      假如 订单已使用一张 10 元优惠券
      当 提交 150 元的订单
      那么 只应享受优惠券的 10 元优惠
```

## 二、Feature：特性

每个文件**必须有且只有一个** Feature，紧跟一句话标题。标题写"能力"而非"页面"：

```gherkin
功能: 会员订单优惠计算     # ✅ 描述业务能力
功能: 优惠计算页测试       # ❌ "页面/测试"不是能力
```

标题之后可以接**自由文本描述**（空行隔开），惯例是"三段式故事"：

```gherkin
功能: 账户登录
  作为一名注册用户          # 谁(角色)
  我希望用账号密码登录       # 想要什么(行为)
  以便访问我的个人信息       # 为了什么(价值)
```

这段描述给"人"看，解析器不校验内容。

## 三、Rule：规则（Gherkin 6 新增）

`Rule` 用来把"同一条业务规则的所有例子"聚在一起。一条规则 = 一组场景；规则下的场景应当**全部验证这条规则**：

```gherkin
规则: 密码连续输错 5 次将锁定账户 30 分钟

  场景: 第 5 次输错后被锁定
    假如 用户已连续输错密码 4 次
    当 用户再次输入错误密码
    那么 账户应被锁定

  场景: 锁定期间密码正确也不能登录
    假如 账户已被锁定
    当 用户输入正确密码
    那么 应提示"账户已锁定,请 30 分钟后再试"
```

**用不用 Rule？** 场景少（≤5 个）可以不用；一旦一个文件里混着多条互不相关的规则，用 Rule 分组，可读性天壤之别。这也是第 3 篇"三层拆解"的基础。

## 四、Background：背景（公共前置）

`Background` 定义该范围（Feature 或 Rule）内**每个场景开头都要执行**的步骤，用于提取重复的"大前提"：

```gherkin
背景:
  假如 系统中存在商品"苹果"且单价 5 元
  假如 用户"小明"的购物车为空

场景: 加入一件商品
  当 用户把 1 件"苹果"加入购物车
  那么 购物车应显示金额 5 元

场景: 加入两件商品
  当 用户把 2 件"苹果"加入购物车
  那么 购物车应显示金额 10 元
```

三条使用纪律：

1. **只放" Given 前置"类步骤**，绝不放 When（动作）和 Then（断言）——否则场景失败时你根本不知道是自己挂的还是背景挂的；
2. 背景**不要写太长**（超过两三步说明场景设计有问题，该用 Rule 重新分组）；
3. 谨慎使用：很多团队规定 Background 最多一两步。

## 五、Scenario：场景

一个场景 = **一个可独立验证的行为例子**，由步骤组成。场景标题也要有信息量：

```gherkin
场景: 余额不足时取款失败              # ✅ 说清"什么条件 + 什么结果"
场景: 测试取款                        # ❌ 零信息
```

## 六、步骤三段论：Given / When / Then

场景内每一步用以下关键词开头（中文对应见第十一节）：

| 关键词 | 语义 | 写什么 |
| --- | --- | --- |
| **Given（假如）** | **已存在的初始状态/前置条件** | "账户余额 100 元""用户已登录"——描述世界当前的样子，不含动作 |
| **When（当）** | **触发行为的关键动作** | "用户申请取款 150 元"——**原则上只写一个核心动作** |
| **Then（那么）** | **可观察的结果/断言** | "应提示余额不足"——验证结果，不描述实现过程 |
| **And（而且）/ But（但是）** | 连接词，继承前一个关键词的语义 | `Given A And B`；`Then X But Y`（But 常用来强调反例） |
| **\*（星号）** | 万能替代词 | 不想纠结三段式时的偷懒写法，不建议常规使用 |

```gherkin
场景: 账户余额充足时取款成功
  假如 用户的账户余额为 100 元
  而且 银行卡有效且未挂失
  当 用户申请取款 80 元
  那么 ATM 应吐出 80 元现金
  而且 账户余额应变为 20 元
  而且 应打印取款凭条
```

**为什么坚持三段式？** 因为它强迫作者想清楚"前置是什么、动一个什么、结果是什么"——场景写得混乱，往往是需求本身没想清楚。这是 Gherkin 超越普通文档的核心机制（方法论细节见第 3 篇）。

## 七、Scenario Outline + Examples：场景大纲（参数化）

一组场景只有数据不同时，不要复制粘贴——用**场景大纲 + 例子表**：

```gherkin
场景大纲: 不同余额下的取款
  假如 用户的账户余额为 <余额> 元
  当 用户申请取款 <取款额> 元
  那么 <结果>

  例子:
    | 余额 | 取款额 | 结果               |
    | 100  | 80     | 取款成功           |
    | 100  | 150    | 提示余额不足       |
    | 0    | 1      | 提示余额不足       |
    | 50   | 50     | 取款成功           |
```

执行时每一行例子变成一个独立场景（上面 4 行 = 4 个场景），`<余额>` 等占位符逐行替换。**例子表是"实例化需求"最直接的表达方式——边界值一目了然。**

## 八、Data Table：数据表（步骤内传结构化数据）

当某一步骤本身需要携带**一组结构化数据**时，在步骤下方缩进写表（以 `|` 分列）：

```gherkin
场景: 批量添加商品到购物车
  假如 购物车为空
  当 用户将以下商品加入购物车:
    | 商品名称 | 数量 | 单价  |
    | 苹果     | 2    | 5.00  |
    | 牛奶     | 1    | 12.50 |
  那么 购物车总金额应为 22.50 元
```

注意与 Examples 的区别：**Examples 属于场景大纲（多场景参数化），Data Table 属于某一步骤（传数据载荷）**——常见用途如注册表单字段、批量导入清单。

## 九、Doc String：多行文本块

步骤需要携带**大段原始文本**（JSON、报文、脚本）时用三个引号包裹：

```gherkin
场景: 提交创建订单的请求
  当 系统收到以下创建订单请求:
    """
    {
      "userId": 1001,
      "items": [{"sku": "A001", "qty": 2}]
    }
    """
  那么 应返回订单号
  而且 订单状态应为"待支付"
```

Doc String 的内容作为**整段字符串**传给该步骤的绑定代码（第 4 篇演示）。缩进不影响内容，引号内的内容原样传递。

## 十、Tags：标签（组织与过滤）

任何结构（Feature/Rule/Scenario/Examples）上方一行以 `@` 开头即为标签，可叠加多个：

```gherkin
@冒烟测试 @支付相关
场景: 微信支付成功
  ...
```

三个用途：

1. **选择性执行**：命令行按标签表达式过滤，如 `cucumber --tags "@冒烟测试 and not @wip"`（支持 and/or/not）；
2. **约定语义**：团队标签字典，如 `@wip`（进行中）、`@慢`（耗时）、`@待产品确认`；
3. **挂元信息**：如 `@需求编号:REQ-1024`（有些团队用标签关联 Jira）。

## 十一、中文关键词：Gherkin 原生支持中文

Gherkin 内置了多语言关键词表（gherkin-languages.json），中文（zh-CN）无需任何配置，直接写即可；也可在文件首行显式声明语言：

```gherkin
# language: zh-CN
功能: 账户登录
  ...
```

**zh-CN 关键词完整对照表**（任选其一均可，多个别名的行表示写哪个都行）：

| 英文 | 中文关键词 |
| --- | --- |
| Feature | 特性 / 功能 |
| Background | 背景 |
| Scenario | 场景 |
| Scenario Outline | 场景大纲 / 剧本大纲 |
| Examples | 例子 / 例集 |
| Rule | 规则 |
| Given | 假如 / 假设 / 假定 |
| When | 当 |
| Then | 那么 |
| And | 而且 / 并且 / 同时 |
| But | 但是 |
| `*` | `*` |

完整中文示例（所有元素一次到齐）：

```gherkin
# language: zh-CN
@回归
特性: 购物车金额计算
  作为一名购物用户
  我希望购物车自动计算金额
  以便在下单前了解费用

  背景:
    假如 用户"小明"已登录

  规则: 多件商品金额累加

    场景大纲: 加入多件商品后的总金额
      假如 购物车中已有 <已有件数> 件单价 5 元的苹果
      当 用户再加入 <新增件数> 件苹果
      那么 购物车应显示总金额 <总金额> 元

      例子:
        | 已有件数 | 新增件数 | 总金额 |
        | 0        | 1        | 5      |
        | 1        | 2        | 15     |

    场景: 批量导入商品
      当 用户导入以下商品清单:
        | 商品 | 数量 |
        | 橘子 | 3    |
      那么 导入应成功

    场景: 提交订单报文
      当 用户提交以下下单请求:
        """
        {"items":[{"sku":"A001","qty":2}]}
        """
      那么 系统应受理该请求
```

## 十二、语法规则速查与常见错误

| 规则/错误 | 说明 |
| --- | --- |
| 一个文件只有一个 `Feature:` | 写两个直接解析失败 |
| 关键词必须行首（可缩进） | `假如` 出现在行中间不算步骤 |
| 步骤不能以标题关键词开头 | 场景里不能再写一个 `场景:` |
| `Examples` 只配 `场景大纲` | 普通场景下写例子表是语法错误 |
| 表格行必须与步骤相邻 | 数据表/DocString 是"上一步骤的载荷"，中间插行会断开归属 |
| 占位符 `<名字>` 只在大纲里有效 | 普通场景写 `<x>` 会被当字面量 |
| 中文关键词与 `:` 之间格式 | `功能:` 用中文冒号或英文冒号均可（官方语言表以 `功能:` 定义），保持全篇一致 |
| 编辑器校验 | IDEA/VS Code 装 Gherkin 插件可实时标红语法错误（第 4 篇） |

## 十三、小结

- 结构记忆：**Feature →（Rule → Background → Scenario）→ 步骤（Given/When/Then + And/But）**；
- 参数化两兄弟：**场景大纲 + 例子表**（多场景）、**数据表 + DocString**（单步骤载荷）；
- Tags 管组织与过滤；`# language: zh-CN` 全中文书写，关键词表任选别名；
- Background 只放前置、Rule 分组规则、场景标题要信息量。

语法到手后，真正拉开差距的是"场景写得好不好"——下一篇专门讲方法与反模式。
